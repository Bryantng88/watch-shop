# QNAP staging worker with ChatGPT login

The image pins Codex CLI 0.166.0. It uses a named permission profile passed through CLI overrides (including when user config is ignored), workspace-write, disabled command networking, and deny-read rules for auth.json, worker secret files and /proc. It does not pass API keys, worker/GitHub tokens or arbitrary CODEX/OPENAI environment variables into the Codex process.

Use three dedicated Docker volumes: /work, /var/lib/codex/auth, and /run/worker (read-only in the worker). API token and optional repository-scoped GitHub token are files api-token and gh-token in the secrets volume, mode 0600. Initialize volume ownership from the image directories as uid/gid 1000. Never mount Docker socket, NAS SSH keys or application env/DB credentials. Root filesystem stays read-only; /tmp is disposable tmpfs. Drop ALL capabilities, set no-new-privileges, publish no ports, and join only the private staging application network. The application internal worker routes remain denied by public ingress.

Authenticate the dedicated auth volume using `codex login --device-auth`. The owner enables device login and completes browser consent; do not copy another Codex executor's auth cache. A successful login is insufficient: verify a real model request and sandboxed tool execution before dispatch.

seccomp-qnap-27.1.2.json is an explicitly selected worker-only profile, derived from Moby v27.1.2 default.json (SHA256 9c1025c88ccaa517b648da571961838744ea2137f176bfe6a48b21294cae9c76). QNAP 27.1.2-qnap8's builtin profile has not been proved byte-identical. The additions permit the observed bubblewrap clone namespace flag combination, unshare NEWUSER, exact mount flag values, pivot_root and umount2 DETACH. They retain default-deny and kernel namespace capability checks. These are additional kernel attack surface, not a general-purpose Docker default. Never install globally or use privileged, SYS_ADMIN or seccomp=unconfined.

Verified on QNAP kernel 5.10.60: upstream baseline rejects user namespace creation; a single unshare NEWUSER exception allows it. The full profile runs the real CLI sandbox with capabilities zero, NNP=1, seccomp=2; workspace writes succeed and outside writes fail. Deny-read canaries fail for auth.json, worker secrets and parent /proc environment. A real ChatGPT-authenticated run invokes a shell and returns the expected result. Unit and mocked lifecycle tests run separately on Linux; they do not replace staging UI acceptance.

Activation: preserve the exact current staging image, AUTH_SECRET, OAuth and token-encryption keys and all HostConfig. Add only PERSONAL_CODEX_ENABLED=1, PERSONAL_CODEX_ENVIRONMENT=staging and the same private API token as the worker. Retain the stopped original container for rollback. Start replacement, verify health, reload only the two existing admin proxies without changing their rules, verify unauthenticated guards and public internal-route denial, then start the worker. Confirm one synthetic UI-dispatched run and result history. Existing tagged tasks are not bulk dispatched.

A GitHub fine-grained token for only Bryantng88/watch-shop needs Contents write and Pull requests write; no Workflows or administrative rights. Store it privately using a no-echo input flow. When draft publishing is enabled the container launcher refuses activation without its dedicated token. Worker pushes only its codex/personal-work/<run-id> branch and opens a draft PR; it never merges/deploys. Missing permissions must fail closed.

Rollback: stop the worker first (terminating its active process groups); stop the new admin app; rename it away; rename the retained original to canonical name and start it; validate/reload the two admin proxies and recheck login/internal deny. Do not restore the database or delete task/run/PR history or auth volumes. Restart policies and compose definitions must be reconciled by deployment tooling when adopting the worker permanently.
