# Order Codex workflow proposal — staging prototype

Feature flag ORDER_CODEX_ENABLED=1 is required in addition to the existing staging-only PERSONAL_CODEX readiness guard. Only active ADMIN users can request/review their own proposals. Production remains disabled. The private worker adds ORDER_CODEX_WORKER=1; its normal personal-work loop remains enabled.

On an order detail page, Yêu cầu Codex accepts text and queues a durable OrderCodexProposal. The worker supplies only order ID/ref, status/payment status, up to 20 item titles/quantities, reference time and timezone; no customer name, phone, address, notes, payment credentials or database connection is supplied. User-entered text is sent to Codex, so users must avoid unnecessary personal data. Order/item text is untrusted data, not authority to execute a command.

The existing dedicated ChatGPT CLI login is reused, no OpenAI API key. An isolated empty planning directory, read-only command sandbox, disabled tool networking and credential/proc/repository deny-read rules are used. JSON output is constrained by order-plan-schema.json and validated again server-side. The planner never gets a business write tool, GitHub token or DB credentials. It can only finish a proposal.

Review shows summary, clarification questions and up to 12 tasks across Sales, Technical, Media, Payment and Operation. A reviewer may edit task title, department, assignee, local date/time, description and prior-step dependencies. Missing facts are not inferred as confirmed payments. Outstanding questions block approval; submit a clarified request. No due date/person is invented when not specified. The prototype stores dependencies as advisory links/notes; it does NOT lock or advance tasks automatically.

Approval is a separate authenticated same-origin command, checks requester/active ADMIN/current order version, validates current assignees, rejects malformed/cyclic/forward dependencies, and creates department TaskItems linked to the order inside one serializable transaction. Revision/status fencing and request-key uniqueness prevent duplicate work on retry/concurrent approval. Repeated approval returns existing IDs. Money, shipment, order status and customer messages are never changed. An order modified after generation requires a new proposal. Records and task activities provide an audit trail.

The legacy migration history cannot bootstrap a blank DB (baseline lacks TaskItem at an old migration); test with an empty synthetic database initialized from the previous Prisma schema, apply exactly the new SQL, then run scripts/smoke-order-codex-workflow.ts.
