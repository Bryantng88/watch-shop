# Work creation event audit — 2026-11-15

Scope: personal work, Ben approval, daily media work, photoshoot scheduling and ad-hoc work creation. This is not a claim that every legacy write path in the application has been audited.

| Path | Event | Commit boundary |
| --- | --- | --- |
| Personal work UI | task.item.created | Managed transaction; consumers after commit |
| Ben personal work approval | task.item.created | Existing approval transaction; committed attempt callbacks only |
| Manual checklist / Ben checklist | task.item.checklist.created | Same transaction as entry; unique eventInstanceId per entry |
| Daily media parent and entries | Both above | Serializable transaction; request-key retry emits nothing again |
| Photoshoot parent | task.item.created | Existing scheduling transaction; reused plan emits nothing again |
| Ad-hoc work, with or without target | task.item.created | Managed transaction; consumers after commit |

Creation payload distinguishes actual actor, personal owner and assignee; includes schedule, work type, tags and canonical object references. Image URLs are presentation data and are excluded. Checklist context is generated by the server. Existing notification and explicit Google Calendar flows remain responsible for their own delivery; these events do not introduce a second push sender.

The new checklist event is registered in the catalog and workspace projection source set. Rollback must remove item, event and delivery together. Entry eventInstanceId prevents outbox deduplication across different entries of the same parent.

Validation: boundary unit tests exercise payload/catalog, after-commit, rollback and idempotent no-op semantics. PostgreSQL fixture scripts additionally cover actual permissions, creation, replay and checklist lifecycle in CI.

Legacy limitation: the broad check-business-event-after-commit checker also flags existing transaction patterns in Ben service, order posting and sales intake. Those pre-existing paths are not refactored wholesale here. The modified Ben approval path explicitly collects callbacks per transaction attempt and drains only after a successful commit; its fixture asserts the canonical creation event.

The older general task action (`src/domains/task/actions/task.actions.ts`) already publishes task.item.created, but records it after the task write rather than inside the same owning transaction. This remains a legacy atomicity gap outside the modified personal/media creation paths; it should be migrated before claiming every task-creation command is atomic.
